# Лабораторная работа 2: параллельная статистика лифтов

Требуется Java 17+ и Maven. Откройте эту папку в IntelliJ IDEA как Maven-проект.

## Данные

Генератор создаёт события от 60 лифтов в 12 зданиях. Для каждого лифта есть
независимая временная линия: при движении от 8 до 24 сообщений на этаж с
интервалом 20–120 мс, после движения редкие сообщения с интервалом 3–20 с.
Интервалы случайны. Очередь по времени объединяет события всех лифтов в
хронологический список. Датчики `POSITION`, `LOAD`, `DOOR`, `MOTOR` имеют
отдельный постоянный `sensorId` для каждого лифта. Каждое событие является
полным снимком состояния лифта; датчик указывает источник сообщения.

В `ElevatorTelemetry.loadKg(long delayNanos)` вызывается `LockSupport.parkNanos`.
Так имитируется ожидание внешнего источника показания. `0` отключает задержку.
Реальное время ожидания зависит от ОС и может превышать указанное значение.

## Три способа расчёта

* `sequential`: `stream()` и стандартный `groupingBy` с обычной `HashMap`.
* `parallel`: `parallelStream()` и `groupingByConcurrent` с `ConcurrentHashMap`.
  Стандартные вложенные коллекторы считают нагрузку и аварии для каждого сенсора.
* `forkJoin`: отдельный `ForkJoinPool` и `RecursiveTask`. Без задержки задачи
  обрабатывают до 256 событий, с задержкой — до 8, чтобы во время ожидания
  было достаточно независимой работы для потоков. Частичные результаты
  объединяются. Возвращается
  `ConcurrentHashMap` с неизменяемой статистикой по каждому сенсору.

Во всех вариантах `loadKg(delayNanos)` вызывается один раз для каждого события.
Генерация и печать отчётов происходят вне JMH-замеров.

## Сборка и демонстрация

В терминале IntelliJ в этой папке выполните:

```powershell
mvn clean package
java -cp target/classes ru.itmo.reactivejava.elevator.App
```

После запуска появится каталог `target/reports`: общий файл `all-sensors.csv`
и четыре отдельных файла `position.csv`, `load.csv`, `door.csv`, `motor.csv`.
В каждом строка соответствует конкретному сенсору с числом событий,
нагрузкой и числом аварий по типам.
`App` дополнительно проверяет совпадение трёх методов на 5000 событиях.

Проверить временные метки, всплески, группы сенсоров и совпадение трёх
расчётов на 50 000 событиях можно так:

```powershell
mvn test-compile
java -cp "target/classes;target/test-classes" ru.itmo.reactivejava.elevator.StatisticsSelfCheck
```

## Замеры JMH

Запускайте JMH из терминала после `mvn clean package`. Отдельный процесс,
прогрев и повторные измерения входят в конфигурацию `@Fork`, `@Warmup`,
`@Measurement`; каждый тест запускается одним внешним JMH-потоком, внутренние
параллельные потоки создают сами алгоритмы.

```powershell
java -jar target/benchmarks.jar NoDelayBenchmark -rf json -rff target/no-delay.json
java -jar target/benchmarks.jar WithDelayBenchmark -rf json -rff target/with-delay.json
py -3 scripts/find_crossover.py target/no-delay.json target/with-delay.json
```

Оба класса измеряют три метода для одинаковых данных при каждом значении `size`.
Первый исследует размеры от 1 до 250 000 без задержки. Второй исследует
размеры от 1 до 1024 с задержкой `50_000` нс на событие. Большие размеры
при задержке намеренно не запускаются: одно измерение заняло бы слишком много
времени. Размеры и задержку можно изменить в `@Param` перед повторным прогоном.

JMH выдаёт время в микросекундах на один полный расчёт коллекции (`us/op`).
Скрипт печатает времена, сообщает, когда интервалы неопределённости JMH
перекрываются, и оценивает точки смены лидера между соседними измеренными
размерами. Несколько смен лидера на малых данных означают, что устойчивого
единственного порога пока не видно. Если пересечения нет, точка может лежать
вне выбранного диапазона. Для более точной оценки добавьте размеры вокруг
найденного интервала и повторите.

Пример реально выполненных замеров с JSON-файлами находится в
`measurements/README.md`. Это данные другого компьютера, их нельзя
выдавать за результаты вашего ноутбука.

Запуск `App` показывает функциональность; время из его запуска не используется
как результат лабораторной. JSON JMH сохраните для отчёта после измерения на
вашем компьютере. При сравнении укажите модель процессора, версию JDK,
количество доступных процессоров и параметры JMH.

## Почему могут отличаться скорости

Без ожидания разбиение задач и синхронизация общей карты могут стоить дороже
самого подсчёта, особенно для маленькой коллекции. С ожиданием показания
параллельная работа перекрывает часть ожиданий, поэтому точка пересечения обычно
сдвигается к меньшему размеру. Собственный ForkJoinPool считает отдельные
частичные карты и реже обновляет общую карту, но выигрыша на каждом размере
не гарантирует. `LockSupport.parkNanos` не равен настоящему запросу к БД:
производительность зависит от планировщика потоков, загрузки компьютера и ОС.

Описание и примеры JMH: https://github.com/openjdk/jmh
