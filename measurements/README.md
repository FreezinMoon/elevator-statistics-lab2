# Пример измерений JMH

Это результаты запуска в рабочем окружении 5 октября 2026 года: Linux,
OpenJDK 17.0.20, 8 доступных JVM процессоров. На ноутбуке времена и точка
пересечения будут другими. Данные сохранены в `no-delay.json` и
`with-delay.json` без ручного изменения. Параметры: один внешний поток JMH,
один fork на комбинацию метода и размера, 2 прогрева по 500 мс, 3 замера
по 700 мс. Значения в таблицах — среднее время полного расчёта, мс.

## Без задержки

| Событий | Stream последовательно | Stream параллельно | Свой ForkJoinPool |
| ---: | ---: | ---: | ---: |
| 5 000 | 0,471 | 0,763 | 1,715 |
| 50 000 | 4,102 | 4,020 | 3,693 |
| 250 000 | 24,547 | 14,683 | 9,895 |

Среди измеренных размеров последовательный stream был быстрее на 16 384
событиях (1,353 против 1,425 мс), параллельный — на 32 768 (2,554 против
2,924 мс). Логарифмическая интерполяция этих двух результатов даёт
приблизительно 18 338 событий. Интервалы ошибок JMH пересекаются; это
ориентир для нового прогона с размерами внутри интервала, а не доказанное
универсальное пороговое значение.

## Задержка 50 000 нс на каждое событие

| Событий | Stream последовательно | Stream параллельно | Свой ForkJoinPool |
| ---: | ---: | ---: | ---: |
| 1 | 0,162 | 0,152 | 0,262 |
| 2 | 0,328 | 0,388 | 0,323 |
| 4 | 0,763 | 0,659 | 0,651 |
| 16 | 2,305 | 1,590 | 1,554 |
| 256 | 40,905 | 8,850 | 6,691 |
| 1 024 | 145,315 | 26,104 | 21,988 |

На малых размерах лидер сменился дважды: интервалы 1–2 и 2–4 события,
интерполированные значения около 1,1 и 2,6. Надёжной единственной точки
равенства этот прогон не устанавливает. Начиная с 4 событий параллельный
stream оказался быстрее в каждой измеренной точке. Фактическое ожидание
`parkNanos(50_000)` на этой ОС может превышать 50 мкс.

Свой ForkJoinPool разбивает список на блоки до 8 событий при задержке и
до 256 событий без неё. Уменьшение блока при ожидании дало больше
одновременных задач. Это видно, например, при 1 024 событиях, где его
время составило 21,988 мс против 26,104 мс у параллельного stream.
На отдельных размерах свой вариант медленнее: затраты на разбиение и
объединение частей тоже входят в измерение.

Для повторения на целевом ноутбуке запустите команды из корневого `README.md`.
После нового прогона скрипт `scripts/find_crossover.py` покажет ваши данные.
Особенно полезно добавить размеры между 16 384 и 32 768 для прогона без
задержки и несколько повторений для размеров 1–8 при задержке.
